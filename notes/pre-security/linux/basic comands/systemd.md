**Systemd** — это подсистема инициализации (PID 1) и системного управления в Linux. Все объекты, которыми управляет Systemd, называются **Юнитами (Units)**. Управление юнитами осуществляется через утилиту `systemctl`, а работа с бинарными логами — через `journalctl`.

---

## Иерархия и типы Юнитов (Units)

### Основные типы юнитов (Расширения файлов):

* `.service` — системная служба или демон (Nginx, SSH, Docker).
* `.target` — группа юнитов, определяющая состояние системы (аналог `runlevel` в SysVinit).
* `.socket` — межпроцессный или сетевой сокет для активации службы при поступлении трафика (Socket Activation).
* `.timer` — таймер планировщика задач (современная альтернатива `cron`).
* `.mount` / `.automount` — управление точками монтирования файловых систем.
* `.path` — активация службы при изменении файлов или директорий на диске.

### Приоритет каталогов конфигурации (от высшего к низшему):

1. `/etc/systemd/system/` — файлы, созданные администратором, и переопределения (локальный приоритет).
2. `/run/systemd/system/` — временные юниты, создаваемые в процессе работы системы (runtime).
3. `/lib/systemd/system/` (или `/usr/lib/systemd/system/`) — юниты по умолчанию, установленные пакетным менеджером.

## Управление службам: systemctl

**Синтаксис:**

```bash
systemctl [команда] [имя_юнита]

```

### 1. Управление жизненным циклом службы

* `start unit` — запустить службу в текущей сессии.
* `stop unit` — остановить работающую службу.
* `restart unit` — перезапустить службу (полный останов и новый запуск).
* `reload unit` — перечитать конфигурационные файлы службы без её остановки (если поддерживается демоном, отправляет `SIGHUP`).
* `status unit` — вывести текущий статус службы, дерево процессов, использование памяти и последние строки лога.
* `is-active unit` — проверить, запущен ли юнит (возвращает `active` или `inactive` и exit-код `0` или `1`).
* `is-failed unit` — проверить, завершилась ли служба с ошибкой (`failed`).

#### Примеры с разбором:

```bash
systemctl status nginx.service

```

> **Что делает:** Выводит состояние службы Nginx, путь к unit-файлу, статус автозапуска, PID главного процесса (`Main PID`), потребление памяти/CPU и последние 10 строк из `journald`.

```bash
systemctl reload-or-restart sshd

```

> **Что делает:** Пытается применить новую конфигурацию SSH без разрыва текущих соединений (`reload`). Если служба не поддерживает безопасную перезагрузку, выполняет полный перезапуск (`restart`).

---

### 2. Управление автозапуском и блокировкой

* `enable unit` — добавить службу в автозапуск при загрузке системы (создает символическую ссылку в `/etc/systemd/system/`).
* `disable unit` — удалить службу из автозапуска (удаляет символическую ссылку).
* `enable --now unit` — включить автозапуск **и немедленно запустить** службу за одну команду.
* `is-enabled unit` — проверить, находится ли служба в автозапуске.
* `mask unit` — полностью заблокировать службу (связывает unit-файл с `/dev/null`). Службу нельзя будет запустить даже вручную или через зависимости.
* `unmask unit` — снять блокировку со службы.

#### Примеры с разбором:

```bash
systemctl mask bluetooth.service

```

> **Что делает:** Жестко блокирует службу Bluetooth. Любая попытка вызова `systemctl start bluetooth` или запуск другими сервисами вернет ошибку `Unit bluetooth.service is masked`.

```bash
systemctl enable --now docker

```

> **Что делает:** Создает симлинк для автозапуска Docker при старте системы и сразу запускает его в текущей сессии, избавляя от вызова `start` и `enable` по отдельности.

---

### 3. Инспекция и управление государством Systemd

* `daemon-reload` — заставить Systemd перечитат все unit-файлы с диска. **Обязательно к выполнению** после любого редактирования `.service` файлов!
* `list-units` — вывести список всех активных и загруженных юнитов в памяти.
* `list-unit-files` — вывести список всех доступных unit-файлов в системе и их статус автозапуска (`enabled`, `disabled`, `masked`, `static`).
* `list-units --failed` — вывести только те юниты, которые завершились со сбоем.
* `reset-failed [unit]` — сбросить счетчик ошибок и статус `failed` у юнитов.

#### Примеры с разбором:

```bash
systemctl list-unit-files --type=service --state=enabled

```

> **Что делает:** Выводит полный список всех сервисов (`--type=service`), настроенных на автоматический запуск при загрузке ОС (`--state=enabled`).

```bash
systemctl edit --full custom.service

```

> **Что делает:** Открывает полною копию файла `custom.service` во временном редакторе и автоматически выполняет `daemon-reload` после сохранения изменений.

---

### 4. Таргеты (Targets) и управление питанием

Таргеты объединяют группы сервисов для достижения определенных состояний системы.

| Старый Runlevel | Target в Systemd | Назначение |
| --- | --- | --- |
| **0** | `poweroff.target` | Выключение системы. |
| **1** | `rescue.target` | Однопользовательский режим восстановления (Single-user). |
| **3** | `multi-user.target` | Многопользовательский консольный режим без GUI. |
| **5** | `graphical.target` | Многопользовательский режим с графической оболочкой (GUI). |
| **6** | `reboot.target` | Перезагрузка системы. |

#### Примеры с разбором:

```bash
systemctl get-default

```

> **Что делает:** Показывает текущий целевой таргет загрузки по умолчанию (например, `graphical.target`).

```bash
systemctl set-default multi-user.target

```

> **Что делает:** Изменяет стандартный режим загрузки системы на консольный режим без запуска графического окружения.

```bash
systemctl isolate rescue.target

```

> **Что делает:** Немедленно переводит систему в режим восстановления, останавливая все некритичные службы и графическую оболочку.

## Анатомия пользовательского .service файла

Для создания собственной службы создается файл `/etc/systemd/system/my-app.service`:

```ini
[Unit]
Description=My Custom Python Application
After=network.target remote-fs.target
Requires=postgresql.service

[Service]
Type=simple
User=appuser
Group=appgroup
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/venv/bin/python main.py
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5s
Environment=PORT=8080

[Install]
WantedBy=multi-user.target

```

### Разбор секций:

* **`[Unit]`** — метаданные и зависимости:
* `After` — запустить сервис строго **после** указанных служб.
* `Requires` — жесткая зависимость: если `postgresql.service` не запущен или упал, `my-app` также остановится.
* `Wants` — мягкая зависимость: попытаться запустить службу, но не останавливать `my-app`, если она недоступна.


* **`[Service]`** — инструкции по запуску:
* `Type` — тип запуска (`simple` — процесс не форкается; `forking` — классический демон с `fork()`; `oneshot` — однократная задача).
* `User`/`Group` — понижение привилегий до указанного пользователя.
* `ExecStart` — абсолютный путь к исполняемому файлу и его аргументам.
* `Restart` — правило автоматического перезапуска (`always`, `on-failure`, `no`).
* `RestartSec` — задержка перед попыткой автоматического перезапуска.


* **`[Install]`** — условия автозапуска:
* `WantedBy` — определяет, при включении какого таргета будет активирован данный сервис.

## Работа с логами: journalctl

Демон `systemd-journald` собирает сообщения из всех доступных источников: логов ядра, вывода `stdout`/`stderr` всех служб, вызовов `syslog` и сообщений аудита. Логи хранятся в эффективном **бинарном формате**.

**Синтаксис:**

```bash
journalctl [флаги] [фильтры]

```

### 1. Навигация и базовые флаги

* `-f` (`--follow`) — режим реального времени (аналог `tail -f`).
* `-n N` (`--lines=N`) — показать последние `N` строк лога (по умолчанию 10).
* `-r` (`--reverse`) — выводить сообщения в обратном порядке (самые свежие вверху).
* `-e` (`--pager-end`) — сразу перейти в конец списка логов в пейджере.
* `-b` (`--boot`) — показать логи только с момента **текущей загрузки**.
* `-b -1` — показать логи за **предыдущую сессию** работы системы.

#### Примеры с разбором:

```bash
journalctl -u nginx.service -f -n 50

```

> **Что делает:** Выводит последние 50 строк лога службы Nginx (`-u nginx.service`) и остается в режиме отслеживания поступления новых записей в реальном времени (`-f`).

```bash
journalctl -b -1 -k

```

> **Что делает:** Фильтрует логи предыдущей загрузки ОС (`-b -1`) и выводит исключительно сообщения от ядра Linux (`-k` или `--dmesg`).

---

### 2. Фильтрация по времени, приоритету и метаданным

#### По времени:

* `--since "YYYY-MM-DD HH:MM:SS"` — выводить логи начиная с указанной даты/времени.
* `--until "YYYY-MM-DD HH:MM:SS"` — выводить логи до указанной даты/времени.
* Поддерживаются относительные значения: `"yesterday"`, `"today"`, `"-1 hour"`, `"-30 min"`.

#### По уровню важности (`-p` / `--priority`):

| Уровень | Имя | Описание |
| --- | --- | --- |
| **0** | `emerg` | Система неработоспособна. |
| **1** | `alert` | Требуется немедленное вмешательство. |
| **2** | `crit` | Критическое состояние системных компонентов. |
| **3** | `err` | Ошибки выполнения. |
| **4** | `warning` | Предупреждения. |
| **5** | `notice` | Нормальные, но значимые события. |
| **6** | `info` | Информационные сообщения. |
| **7** | `debug` | Отладочная информация. |

#### Примеры с разбором:

```bash
journalctl -u docker.service --since "2026-08-11 10:00:00" --until "12:00:00"

```

> **Что делает:** Показывает логи службы Docker строго за двухчасовой интервал указанной даты.

```bash
journalctl -p err..emerg -b

```

> **Что делает:** Выводит логи текущей сессии (`-b`) с уровнем важности от `err` (3) до `emerg` (0), скрывая предупреждения и информационные сообщения.

```bash
journalctl _UID=1000 _COMM=sshd

```

> **Что делает:** Применяет низкоуровневую фильтрацию по полям структур `journald`: выбирает записи, сгенерированные процессом `sshd` (`_COMM`), который выполнялся от имени пользователя с UID 1000.

---

### 3. Форматирование вывода и управление диском

* `-o FORMAT` (`--output=FORMAT`) — выбор формата вывода данных:
* `short` — стандартный формат `syslog` (по умолчанию).
* `json` / `json-pretty` — вывод логов в формате JSON (удобно для парсинга).
* `verbose` — выводит **все внутренние метаполя** каждой записи лога.
* `cat` — выводит только чистые сообщения без временных меток и имён хостов.


* `--disk-usage` — показать текущий объем диска, занятый файлами журналов.
* `--vacuum-size=SIZE` — очистить старые логи, оставив указанный максимальный объем (например, `500M`).
* `--vacuum-time=TIME` — удалить логи старше указанного периода (например, `2weeks` или `1month`).

#### Примеры с разбором:

```bash
journalctl -u nginx -o json-pretty -n 1

```

> **Что делает:** Выводит последнюю запись лога Nginx в развернутом виде со всеми внутренними атрибутами `journald` (включая PID, cgroup, контекст SELinux/AppArmor) в формате JSON.

```bash
sudo journalctl --vacuum-size=1G

```

> **Что делает:** Удаляет самые старые архивные бинарные файлы логов до тех пор, пока суммарный размер журнала на диске не станет равен или меньше 1 Гигабайта.

## Сводная сравнительная матрица утилит

| Задача | Команда |
| --- | --- |
| **Запустить / Остановить сервис** | `systemctl start|stop <service>` |
| **Добавить в автозапуск и запустить** | `systemctl enable --now <service>` |
| **Применить изменения в `.service` файле** | `systemctl daemon-reload` |
| **Посмотреть почему упал сервис** | `systemctl status <service>` или `journalctl -u <service> -e` |
| **Смотреть логи сервиса в реальном времени** | `journalctl -u <service> -f` |
| **Найти ошибки в логах за сегодня** | `journalctl -p err..emerg --since today` |
| **Очистить дисковое пространство от логов** | `journalctl --vacuum-time=7d` |
